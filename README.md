# dsh-astudio-connect

[English](./README.en.md) | 中文

将 AStudio 应用中已登录的模型接入 [DeepSeek Harness (DSH)](https://github.com/deepseek-ai/deepseek-harness)，零配置使用。

参考 [dsh-workbuddy-connect](https://github.com/corrinehu/dsh-workbuddy-connect) 的设计思路，针对 AStudio 的 maas-api（标准 OpenAI 协议）大幅精简。

> **零配置**：复用你本机 AStudio 的登录凭证，不重新登录，不落盘。

## 安装

### 前置

- 本机已安装 Node.js `^22.19.0 || >=24.0.0`
- 一个讯飞账号：在 DSH 设置页微信扫码登录即可，**不需要安装 AStudio**；若本机已装并登录过 AStudio，插件也会直接复用那次的凭据
- DeepSeek Harness 运行时，版本要求见 [DSH 版本支持](#dsh-版本支持)

### 安装插件

**命令行**：

```bash
dsh plugin --profile web add dsh-astudio-connect@latest
```

把 `web` 换成你实际启动的 profile 名。

> 插件版本要与 DSH 内核代次对齐，否则宿主会直接拒载。装最新版即可；仍被拒载请把 DSH 内核版本和完整报错提到 [Issues](https://github.com/Cwentor/dsh-astudio-connect/issues)，不要绕过宿主校验。

### 验证

装完必须**完全退出并重启 DSH**，然后确认：

1. 模型选择器里出现 **AStudio** 分组；
2. 从分组里选一个模型，完成一次简短对话并能正常回复。

两条都满足才算安装成功。若分组不出现，到 profile 目录（`$DSH_HOME/profiles/<name>`）里跑 `npx dsh-astudio-connect doctor` 看登录态。

> 也可以把安装交给本机已有的 Agent（DSH Agent、Codex、Claude Code、Cursor 等），把下面这段话原样发给它：
>
> 请帮我安装并验证 DSH（DeepSeek Harness）插件 dsh-astudio-connect（npm 包名：`dsh-astudio-connect`）：
> 先阅读项目 README，确认我实际使用的界面（Web / Desktop / TUI）与 DSH 内核版本；
> Desktop 走「插件」面板的「添加插件」，填包名 `dsh-astudio-connect`；命令行 profile 用 `dsh plugin --profile <name> add dsh-astudio-connect@latest`，不要改依赖包或绕过宿主校验；
> 若宿主因版本代次不匹配拒载，把我的 DSH 内核版本和完整报错给我；
> 任何本地文件或配置改动，先征得我同意并做好备份；
> 装完后验证模型选择器里出现 AStudio 分组，并陪我完成一次简短对话。

## 功能

- **开箱即用**：安装并启用插件后即可在 DSH 中直接使用，无需额外配置。
- **凭证复用**：读取 AStudio 的 `experimental_bearer_token`，无需额外 OAuth 流程。
- **标准协议**：maas-api 是标准 OpenAI 兼容协议，pi-ai 原生支持，无需协议转换。
- **全能力桥接**：非流式、流式 SSE、工具调用、推理模型的 `reasoning_content`、上下文压缩，全部沿用 DSH 宿主自己的实现。
- **模型目录**：完全取自 AStudio 自己的 model-manager 接口，带真实的上下文窗口与最大输出；插件不内置任何清单，取不到就显示「无可用模型」。
- **推理档位探测**：对未声明档位的模型，由你主动授权后发送带哨兵的最小请求，确认上游真的校验 `reasoning_effort`，再逐项确认接受哪些档位。
- **模型显隐**：在设置卡片里勾选要在选择器中显示的模型；关掉的模型立刻从选择器消失，正用着它的会话需要另选模型才能继续发送。
- **积分与领取**：设置页新增「AStudio 积分」分区，列出账户的通用 / 星火两份余额，带「刷新」和「领取每日登录积分」，不用打开 AStudio 客户端，也不用先选中 AStudio 模型。
- **设置卡片**：侧栏「插件」面板下的 AStudio Connect 卡片，分「账户 / 模型 / 探测」三个分区，可手动刷新目录、逐个探测。
- **命令行诊断**：`status` / `doctor` / `logout` 三个命令，全程不输出 token 材料。
- **更新检查**：对照 npm 公共 dist-tags 判断是否有新版本，并用 GitHub releases 补充说明。

## 配置

插件配置通过 DSH 的插件页管理（0.2.x 在侧栏「插件」面板 → AStudio Connect）：

| 字段 | 说明 |
|------|------|
| `displayName` | 模型选择器中显示的 provider 名称（默认 `AStudio`） |
| `configPath` | 自定义 AStudio `config.toml` 路径 |

`cordis.patch.yml` 只注册插件，不改动 profile 当前的默认模型。

## 模型目录

模型清单与上下文参数来自 AStudio 的 **model-manager** 接口。

**目录解析规则：**

- 只收 `visibility` 为 `list` 的模型，`supported_in_api` 为 `false` 的不收；上下文窗口或最大输出缺失的行也丢弃；
- 上下文窗口与最大输出取自上游真实值（例如 `spark-x2.6-preview` 为 262144 / 100000）。

**插件不内置任何模型清单**，列表完全以上游实际返回为准：

1. 实时目录 —— 上游本次返回的模型；
2. 上次成功快照 —— 上游这次没取到（网络、鉴权、响应异常）时的上一次结果，仍是上游数据；
3. 两者都没有 —— 列表为空。

第 3 种情况不用内置清单、占位或默认模型顶替：设置卡片显示「无可用模型」并说明原因（未登录 / 接口报错 / 响应无法解析 / 连不上 / 上游确实没列），模型选择器显示宿主的「暂无可用模型」。上游**明确返回空列表**同样按「无可用模型」处理并写入快照，否则之后一次失败的刷新会把已下架的模型顶回来。上游应答里若 `models` 字段缺失、类型不对，或所有行都不可用，则视为响应异常而不是「上游撤下了全部模型」，此时不覆盖已有快照。

## 推理档位与探测

WorkBuddy 类上游的推理档位信息分散在上游接口与客户端私有 UI 逻辑里，且模型目录变化很快。若插件凭经验为所有未声明模型补齐统一档位，就得持续追赶这些未公开、没有稳定契约的产品逻辑。

实测还发现，有些模型虽然接受 `reasoning_effort` 参数，却可能忽略未知值并回退到默认行为——一次请求返回成功，并不能证明某个档位真实可用。

因此本插件采用**用户主动授权触发、动态获取档位**的方式：

1. 设置卡片的「探测」分区对未声明档位的模型提供「探测 / 重新探测」；
2. 点击后插件发送带哨兵字符串的最小请求（`max_tokens: 1`，单请求超时 30 秒）；
3. 上游接受 → 记为 `validating`，只保存被接受的档位；上游以 `invalid_parameter_value` 拒绝 → 记为 `rejected` / `non-validating`；
4. 结果按 `account:modelId` 持久化，保留 24 小时后过期撤销。

探测会向上游发一次真实请求，消耗少量上游 token（与插件里其它调用一样，计入的是上游用量，不是 AStudio 积分——见[计费与积分](#计费与积分)）。结果只表示当前上游接受该档位，**不承诺它一定改变推理效果或速度**。

`reasoning_effort` 到 pi-ai 档位的映射只开放上游声明过的档位；`off` 仅在模型声明了 `none`（即可关闭思考）时才开放，并且**发出去的值是 `none` 而不是 `off`**——上游的词汇表只有 `none` / `high` / `max`，实测传 `off` 会被整包拒成 10005。

## 模型显隐

在设置卡片的「上下文」分区可以勾选要在模型选择器中显示的模型。隐藏配置写在 `$DSH_HOME/.astudio-connect/model-visibility.json`，按本地身份保存。

- **只影响可选性**：隐藏的模型不出现在 picker、`listModels()` 和 shim 的 `/v1/models` 里；但正在使用该模型的已有会话不受影响，`resolveModel()` 不做过滤。
- **新账号和新上架模型默认显示**。

AStudio 的 token 不携带稳定 uid，因此本插件只有一个本地身份 `astudio-local`——目录快照、显隐偏好和探测记录都挂在它名下，不做多账号隔离。

## 积分与每日领取

设置页左侧导航最下方有一行「AStudio 积分」，点开就是账户的两份余额与两个动作：

```
通用积分                            1393
────────────────────────────────────────
星火积分                           24621
────────────────────────────────────────
每日登录奖励每天一份…         [领取]  [刷新]
```

两份积分分开显示、**不相加**，因为用途不同：

- **通用积分**（`totalBalance`）：所有模型，以及插件、Skill 调用等费用（这里是 AStudio 自身的插件与 Skill 调用，**不含本插件**）。
- **星火专属积分**（`sparkTotalBalance`）：仅星火模型的消耗。

数据来自 AStudio 桌面端自己使用的账户接口（`https://agent.xfyun.cn/xingchen-studio/points/balance`）。AStudio 的设置页会请求它自己的 loopback 服务，该服务带着桌面会话 Cookie 转发到账户 API；本插件直接用同一个 `ssoSessionId` 访问同一个上游，因此**不需要 AStudio 正在运行**。这个 Cookie 有两个可能的来源：插件自己扫码登录得到的，或者 AStudio 写在 `astron-session.json` 里的——前者优先，见下面的[微信扫码登录](#微信扫码登录)。

> `ssoSessionId` 与模型目录用的 `modelBearerToken`、聊天用的 `experimental_bearer_token` 都在同一个文件里，但是三份不同用途的凭据。

行为约定：

- **读取时机**：打开这个分区时读一次，点「刷新」再读一次。**余额不做定时轮询**——每次读取都会打一次上游。（唯一按秒问上游的是登录时那张二维码，见[微信扫码登录](#微信扫码登录)。）
- **与会话无关**：这一页不看当前选中的模型，没选 AStudio 模型、甚至开着别家模型的会话也能看余额。（这项能力原来挂在输入框的徽标上，只能在该会话选中 AStudio 模型时出现。）
- **打开即最新**：面板挂载时的读取带 `?refresh=1`，绕过宿主侧的 30 秒缓存。打开设置页是「我现在有多少」的明确提问，给它一个 30 秒前的数字没有意义。
- **失败绝不显示假数字**：读不到就显示 `—` 并说明原因，不会把「读不懂」渲染成 `0`。
- **失败不缓存**，下次读取重新问上游。

| 情况 | 表现 |
|---|---|
| 网络失败 / 上游异常 | 数字显示 `—`，提示「账户接口没有返回可读的余额」，「刷新」可重试 |
| 登录已失效（上游 `code: 80000`，或 401/403） | 提示「AStudio 登录已失效」，需在 AStudio 重新登录 |
| 账户没有星火积分池 | 只显示通用积分，不显示 0 |
| 余额确实为 0 | 正常显示 `0`（0 是真实余额，不是未知） |
| 从未在 AStudio 登录 | 提示「AStudio 未登录」，「领取」置灰（没有会话可领） |

> **已知限制**：账户接口只提供聚合余额，没有逐笔明细——AStudio 桌面端本身也是如此（它引导用户去网页查看明细）。因此这一页能反映「余额变化」，但无法给出「这一轮对话精确扣了多少」。

> **用插件对话时，这个数字不会变化。** 余额不变不等于没花钱，而是这笔调用压根没走 AStudio 那本账——机制见[计费与积分](#计费与积分)。

### 微信扫码登录

这一栏最上面的卡片管登录。**不需要安装或打开 AStudio**：扫一个微信二维码，插件自己去换模型密钥，凭据存在 `$DSH_HOME/.astudio-login.json`（权限 `0600`，仅本用户可读）。

它走的就是 AStudio 桌面端自己的那三步，全是普通 HTTPS，没有设备指纹、没有签名、不碰本地服务：

```
GET  sso.xfyun.cn/SSOService/wx/scanlogin/qrcode?fd=<票据>   → 微信二维码图片地址
GET  sso.xfyun.cn/SSOService/wx/scanlogin/uids?fd=<票据>     → 未扫 code -1；已扫返回 infoList[{uid, ssoSessionId}]
GET  agent.xfyun.cn/xingchen-studio/bot/models/configs       → Cookie 用上面的 ssoSessionId，每行带 api_key
```

那个 `api_key` 与 AStudio 存成 `experimental_bearer_token` 的是同一种值，所以登录完成后，对话、目录、探测、余额、领取全都照旧工作——只是凭据来源换成了插件自己。票据 `fd` 是 8 位、从 AStudio 自己那套去掉了 `I/l/0/1/o/O` 的字母表里取，有效期约一分钟。

| 情况 | 表现 |
|---|---|
| 没有任何登录 | 「没有可用的登录」+「微信扫码登录」 |
| 正在用客户端的登录 | 「正在使用 AStudio 客户端的登录」，仍可扫码替换 |
| 扫码前 | 显示二维码 +「等待扫码…」，每 2 秒问一次，过期后提示「二维码已过期」 |
| 该微信绑了多个账号 | 列出账号名，点一个即完成 |
| 该微信未绑定 AStudio 账号 | 「该微信未绑定 AStudio 账号」，二维码留着，可换个微信扫 |
| 扫码成功但账号没有模型凭证 | 「已登录，但该账号没有可用的模型凭证」，这种情况不落盘 |
| 登录成功 | 「已通过 DSH 扫码登录 · 账号 …」，右侧变「退出登录」 |

优先级是**插件自己的登录压过 AStudio 的文件**。理由很直接：在这里扫码的人已经指定了要用哪个账号；退一步悄悄回落到一个可能早已卸载的客户端的旧文件，会让扫码看起来像坏了。「退出登录」只删本插件那个文件，AStudio 自己的会话原样不动，随后自动回落到它。

> 二维码图片由宿主取回后以 data URL 内联给页面，浏览器不加载任何第三方来源的资源。

### 每日登录积分

余额下方还有一个「领取」按钮，用来领取 AStudio 的每日登录积分（金额随套餐：试用 100 / 基础 200 / Pro·Enjoy 400），**不需要打开 AStudio 客户端，也不需要装它**。

它看起来像一个签到动作，实际是三步，和桌面端启动时做的事完全相同：

1. `POST tenant-app/v2/init-app` —— 桌面端每次启动都会调它，服务端**在这一步**结算当天的登录奖励并把积分打进账户。
2. `GET client-popups/pending` —— 取出那条 `DAILY_REWARD_DIALOG` 弹窗（`popupId` + `instanceKey`）。
3. `POST client-popups/complete` —— 把弹窗关掉。

关键在第一步。`pending` 自己不会产生任何东西：不调 `init-app`，服务端就不认为今天有客户端上线过，那个列表永远是空的——这正是 `0.2.2` 及更早版本“只有客户端开着才领得到”的全部原因。

实测（`2026-11-05`，客户端完全没开，起点余额 7793）：

| 步骤 | 余额 | `pending` 里的每日弹窗 |
|---|---|---|
| 基线 | 7793 | 0 |
| `POST tenant-app/v2/init-app` | **7893** | **1** |
| 再调两次 `init-app` | 7893 | 1 |
| `POST client-popups/complete` | 7893 | 0 |

+100 出现在 `init-app` 那一步，`complete` 前后余额一分没变——**弹窗只是通知，不是入账凭证**。桌面端之所以“点一下就领到”，是因为它在渲染弹窗之前就已经自己 `complete` 过了，界面上那个按钮是装饰。

金额也不从弹窗里读：当前客户端下发的 `payload` 只有 `title` / `content` / `confirmText`，一个数字都没有（早期版本的文档按 `payload.points` 记录，那是旧包的结构）。插件改为在 `init-app` 前后各读一次余额，用差值作为本次入账额；两次都读不到时不显示 `+N`，只显示「已领取」。

幂等由上游保证：同一天重复 `init-app` 不会重复加分，重复 `complete` 也照常返回成功，所以多点几次不会多加分。

| 结果 | 表现 |
|---|---|
| 余额增加 | 就地更新，按钮左侧显示 `+100`（绿色），6 秒后淡出 |
| 弹窗关掉了但余额没动（今天早已入账） | 显示「今日已领过」，余额不动 |
| `init-app` 成功、没弹窗、余额没动 | 显示「今天没有新的积分入账——今日奖励可能已经领过，或当前套餐不含每日奖励」 |
| 登录已失效（`code: 80000` 或 401/403） | 数字清空并显示「登录已失效」 |
| 上游异常 / 平台无对应 `clientType` | 显示「暂不可用」 |

「今日已领过」只在一种情况下给出：弹窗存在、被关掉了、而余额一分没动——这证明这笔钱在你点之前就在账上（典型是客户端拉到了弹窗却没来得及关就退了）。反过来，`init-app` 成功、列表为空、余额没动，说明服务端结算过但没发，这时说「已领过」就是猜测，所以那一行写成「今天没有新的积分入账」。

`clientType`（Windows `21` / macOS `22`）与 `studioVersion` 是硬性要求（缺任一个，网关直接回 `11001001`）。桌面端还会给所有讯飞域名的请求额外加一个 `clientVersion`（两者都取自 `electron.app.getVersion()`，当前是 `3.6.0`）；插件三个头都发，保持与客户端请求一致。版本号只做形态校验，所以用常量而不是去读已安装的 AStudio 版本——这正是它能做到「不需要装 AStudio」的原因。

`pending` 的返回里还有一个必须按原样解析的细节：`popupId` 是**正整数**，`complete` 上游也用 `Number.isSafeInteger` 校验，客户端拿到字符串会直接判定整条弹窗配置非法。插件早期按字符串收，结果服务端下发的每一条奖励都被自己过滤掉了，界面照样报「今日已领过」，而奖励其实还老老实实躺在服务端——客户端一点就能领。现在按客户端的方式解析，非正整数的 id（例如预览用的 `-3`）直接跳过。

这几个接口同时是按**账户**鉴权的：桌面端每个账号请求都带 `ssoSessionId`、`sso_sessionid`、`account_id`、`token` 四个 cookie。插件现在也照原样带上（早期只带 `ssoSessionId`）。

> 这是本插件**唯一**会改动账户状态的接口（`POST /astudio/claim`）。它内部发出的写请求只有两个：`init-app`（桌面端启动时自己也调，服务端据此结算当天奖励）和 `complete`（只针对 `DAILY_REWARD_DIALOG`）。它不改本地任何文件，也不碰 `pending` 里其它类型的弹窗（公告、功能引导等）：不理解的弹窗一律代用户完成，等于替用户做了一个不知道是什么的决定。

若这一页显示「暂不可用」而「刷新」也无效，先确认插件产物是否与运行中的 DSH 版本匹配：DSH 在启动时加载插件，重新构建后必须**完全退出并重启 DSH**（仅刷新页面不够）。整行导航都不见了，则说明当前装的插件版本早于这个分区——它和输入框徽标是同一批改动，徽标被替换成了这一页。

## 计费与积分

> **先说结论**：插件发起的调用**不消耗 AStudio 积分**。AStudio 的积分不由模型网关注销，而是桌面端按「轮次」自报用量后结算。插件是一个完全独立的进程，天生不在这条链路上。

真正扣钱的是桌面端，不是 `maas-api`：

1. acode 运行时开启一个 turn（带 `turn_id` / `thread_id` / `session_id`）；
2. 每次模型请求经桌面端的本地模型网关转发到 `model_providers.astron-spark.base_url`，网关把该请求的 input / output / cached token 作为 runtime event 记下来；
3. 轮次结束后，桌面端聚合成一份 `ClientTurnUsageReport`（schema 1.3），写入 `state.sqlite` 的 `turn_billing_outbox`；
4. `DirectPointsGateway.settle()` 带着桌面会话 Cookie `POST {studioApiBaseUrl}points/deduce-balance`，服务端据此算出 `ratedPoints`，扣 `GENERAL_POINTS` / `SPARK_POINTS`。

被计入积分需要同时满足三个条件：请求属于某个 acode turn、该 turn 以 `completed` 收尾、结算请求提交成功。缺任何一条都不扣费——**只是「请求从那个网关出去」并不够**。

### 这不等于「免费」

- **上游 token 照常消耗**，只是不进 AStudio 那本账；
- **余额闸门覆盖不到插件**：AStudio 在自己余额为 0 时会以 `402 astron_points_exhausted` 拦住请求，而这个判断发生在它自己的本地网关上；插件不经过那里，因此理论上余额为 0 时仍可发起调用（未实测，按当前实现推断）；
- **上游随时可以把计量下沉到网关**，改成按 uid / token 记账。那一天到来时这条通道会立即关闭，插件不需要改任何一行代码；
- **不要试图让插件「补上报」**：`ClientTurnUsageReport` 里的 `session_id` / `thread_id` / `call_ids` / `capability_usages` 只有 acode 运行时才产得出来，服务端另有 `turn_billing_usage_reviews` 做缺失审计。拼凑一份报告只会进审计表，不会让账变正确。

积分页面读的就是 AStudio 自己的账本，用插件聊天时它当然不动——**余额不变不代表没花钱，只代表没走那本账**。使用前请先读[免责声明](#免责声明)。

## 设置卡片

侧栏「插件」面板 → AStudio Connect，一张卡片分三个分区，随插件语言切换中英文：

- **账户**：登录态、目录来源（实时 / 已保存 / 无可用模型）、模型数，以及一键刷新目录。
- **模型**：每个模型一个显隐开关，改完必须点「保存」才写入——关掉的模型立刻从 DSH 的模型选择器里消失。若某个会话正用着被关掉的模型，它需要另选一个模型才能继续发送。未保存时卡片标题栏显示「未保存 n」，正文显示「保存后向 DSH 暴露 n / m」，另有「撤销」丢弃本次改动。
- **探测**：每个模型的探测状态与已接受档位，可逐个探测 / 重新探测。按钮按下即变「探测中…」，同时给出按下位移与触感提示（平台支持时）。

卡片挂载时读一次状态文档，之后每 60 秒重新读取一次；数据全部来自同源的 `GET /astudio/status`，不携带任何 token 材料。

### 同源路由一览

| 路径 | 方法 | 用途 | 防护 |
|---|---|---|---|
| `/astudio/status` | `GET` | 状态文档 | loopback Host + Origin |
| `/astudio/points` | `GET` | 积分余额（`?refresh=1` 绕过缓存） | loopback Host + Origin |
| `/astudio/claim` | `POST` | 领取每日登录积分 | loopback Host + Origin + 进程内控制密钥 |
| `/astudio/login/qr` | `POST` | 生成扫码登录票据与二维码 | loopback Host + Origin + 进程内控制密钥 |
| `/astudio/login/qr/poll` | `POST` | 查询扫码状态，扫到即换取并保存凭据 | loopback Host + Origin + 进程内控制密钥 |
| `/astudio/login/logout` | `POST` | 清除插件自己的登录（不动客户端会话） | loopback Host + Origin + 进程内控制密钥 |
| `/astudio/update` | `GET` | 版本与更新信息 | loopback Host + Origin |
| `/astudio/probe/{modelId}` | `POST` | 推理档位探测 | loopback Host + Origin + 进程内控制密钥 |
| `/astudio/visibility/{modelId}` | `POST` | 模型显隐（每改一个模型一条，由「保存」触发） | loopback Host + Origin + 进程内控制密钥 |

五条写路由（探测、显隐、领取、扫码登录的两条）要求同一个进程内控制密钥（随状态文档下发、每进程轮换、不落盘）：状态路由的 loopback 校验挡住的是 DNS 重绑定的**页面**，那并不等于授权了一个**会改状态**的操作。领取这条还多一层 Origin 校验——跨站 `fetch` 一样能打到 `127.0.0.1`，而「别的网页替我领了积分」正是要挡住的那件事。

| `0.2.3` | `^0.2.1-rc.2`（`0.2.1-rc.2` 起，`0.3.0` 以下） |
| `0.2.2` | `^0.2.1-rc.2`（`0.2.1-rc.2` 起，`0.3.0` 以下） |
| `0.2.1` | `^0.2.1-rc.2`（`0.2.1-rc.2` 起，`0.3.0` 以下） |
| `0.2.0` | `^0.2.1-rc.2`（`0.2.1-rc.2` 起，`0.3.0` 以下） |
| `0.1.1` | `^0.2.1-rc.2`（`0.2.1-rc.2` 起，`0.3.0` 以下） |
| `0.1.0` | `0.2.0-rc.2`（精确版本） |

插件在 `peerDependencies` 里声明内核范围，宿主的 `evaluatePluginCompatibility` 逐项用 semver 校验，范围不满足时直接拒载。`0.1.0` 把版本钉死成 `0.2.0-rc.2`，因此内核每推一个 rc 都得跟着发版；`0.1.1` 起改为 `^0.2.1-rc.2`，覆盖 `0.2.1` 这一代的全部预发布与正式版（`rc.3`、`rc.4`、`rc.5` 均可直接加载），只有跨到 `0.3.x` 才需要发布新版本。`0.1.0` 是对着 `0.2.0-rc.2` 发布的，那一代是实机验证环境；`0.1.1` 一代下 provider 注册、设置卡片、积分分区由本地单元测试与集成测试覆盖，桌面端具体构建号仍需在新内核上重新确认。

`0.2.0` 的内核范围与 `0.1.1` 完全一致，发的只有功能：设置页的积分分区（看余额、领每日积分）与微信扫码登录。升级前需要知道一件事——**从 `0.2.0` 起插件会在本地落盘一个凭据文件**。这是扫码登录的必然结果：不装客户端就只能自己存会话。文件是 `$DSH_HOME/.astudio-login.json`，权限 `0600`，只在你主动扫码或点「退出登录」时增删；如果你只想要「读完客户端凭据就走、一个字节也不写」的旧行为，留在 `0.1.1`。

`0.2.1` 是纯修复版，内核范围不变。**装了 `0.2.0` 的请升级：那一版的「领取」按钮实际领不到积分。** 待领弹窗的 `popupId` 是正整数，插件却按字符串接收，于是每条真实奖励都在本地被过滤掉，界面一律报「今日已领过」，而奖励还挂在服务端——打开 AStudio 客户端照样能领。`0.2.1` 按客户端的方式解析 id，把「待领列表为空」与「上游明确回 `11003002`」拆成两种结果，领取请求也补齐了按账户鉴权的四个 cookie。

`0.2.2` 只做请求头对齐，**不解决「只有客户端开着才能领」那个现象**。改动有两处：新增 `clientVersion`（常量 `3.6.0`），`studioVersion` 从 `3.5.5` 提到 `3.6.0`——桌面端的 `fetchWithClientVersion` 会给所有讯飞域名请求加这个头，插件此前完全没有发过。发版前后的 A/B 实测表明这个头不是原因（见[已知限制](#已知限制)），所以这版的实际价值是把「插件发出的请求与客户端无法区分」这件事做实，以及把「每日奖励只在桌面端启动后才下发」这个限制如实写进文档。谁要是在版本说明里看到这版修好了领取，那话说错了。

`0.2.3` 修的才是真正的根因，**这版真的能脱离客户端领取了**，内核范围不变。缺少的不是请求头（`0.2.2` 猜的那件事，A/B 已经证伪），而是一个调用：桌面端每次启动都会 `POST tenant-app/v2/init-app`，服务端**在这一步**结算当天的登录奖励并把积分打进账户；不调它，`client-popups/pending` 一整天都是空列表。实测（`2026-11-05`，客户端完全未运行，起点余额 7793）：调用前待领列表 0 条、调用后余额 7893 且出现一条弹窗，重复调用不再加分，`complete` 前后余额不变——所以弹窗只是通知，`complete` 只是关掉它。领取按钮现在按「读余额 → init-app → 读弹窗 → 关弹窗 → 再读余额」执行，金额取两次余额的差值（当前客户端的 `payload` 里根本没有金额字段）。顺带修掉一个文档外的问题：`ASTRO_VERSION` 这个常量从 `0.1.0` 起就没再动过，导致「检查更新」和心跳上报一直在报一个早已不存在的版本号；现在与 `package.json` 对齐，并加了断言防止再次漂移。

## 请求被上游拒绝时

maas-api 对不合规的请求只回一句 `10005 invalid request`，不说明是哪个字段。插件按下面的顺序自愈，全部发生在转发层，DSH 与 pi-ai 不需要改动：

1. **线格式修复**：`tool_calls[].function.arguments` 不是字符串、`tool` 消息没有 `tool_call_id`、`content` 为 `null` —— 这些都是任何 OpenAI 兼容服务都不接受的形状，直接就地修好并记一条 warn。
2. **推理档位守卫**：请求里的 `reasoning_effort` 若不在该模型声明的档位内（或模型根本不支持推理），直接去掉该字段。网关是按模型校验这个值的，发了不存在的档位就是整包 400。
3. **形状回退**：去掉 `store` / `stream_options` / `prompt_cache_key` 等平台专有字段、`developer` 角色改写为 `system`；仍然 400 就把纯文本 content 数组压平成字符串。一旦某种形状被接受，本进程后续请求直接用它，不再多花往返。
4. **自诊断（每个进程最多一次）**：四种形状都被拒时，插件反过来问网关——依次只改一个维度（`max_tokens`、整份 `tools`、`reasoning_effort`、消息历史），再对出问题的那一项做二分查找。诊断结论会写进返回给 DSH 的错误信息（`diagnosis: ...`），能被诊断出的问题会**自动修好并重发**，修复在整个进程内保持：
   - `max_tokens` 超限 → 压到 8192；
   - 某个工具定义被拒 → 丢掉那一项（按名字记日志），其余工具照常生效；
   - 档位不被接受 → 去掉 `reasoning_effort`。

`store` 默认就不发（`supportsStore: false`），所以正常情况下第 1–3 步不会触发，也不产生额外请求。

被拒的请求体还会写一份到 `%TEMP%\dsh-astudio-connect\failed-requests\`（最多保留 5 份，单份上限 16 MB），因为只有真实请求体能看出网关到底不接受什么。该文件含对话正文，只在本机；设 `ASTUDIO_DUMP_FAILED=0` 可关闭，`ASTUDIO_DUMP_FAILED_DIR` 可改目录。

## 已知限制

- [ ] **图片输入尚未启用**：adapter 已按目录声明把模型映射为 `input: ['text', 'image']`，但 model-manager 的解析目前固定 `supportsImages: false`（上游文档里也没有对应字段），因此当前所有模型都只接受纯文字。
- [ ] **当前只支持 Windows**：macOS / Linux 未做适配与验证，不保证可用。
- [ ] **只有一个本地身份**：AStudio token 不携带稳定 uid，目录快照、显隐偏好和探测记录都挂在 `astudio-local` 名下，不做多账号隔离。
- [ ] **插件调用不计入 AStudio 积分**：积分由桌面端按 turn 自报结算，插件不产生 turn，因此不扣费；这实际上是一条不被计量的通道，见[计费与积分](#计费与积分)。这里不提供任何补齐上报的能力。
- [ ] **余额闸门不覆盖插件**：AStudio 自己在余额为 0 时返回 `402`，该判断在它的本地网关内；插件绕过该网关，所以余额耗尽也不会被它拦住（推断，未实测）。
- [ ] **不做逐笔扣费明细**：账户接口只给聚合余额，设置页只能反映余额变化；插件调用则完全不产生扣费记录，更谈不上明细。
- [ ] **不承诺长期兼容上游私有接口**：模型目录、账户接口与推理档位信息都是 AStudio 客户端自己的接口而非官方开放 API，上游改动可能使插件失效；届时插件按「上次成功目录」降级，连快照都没有时如实显示无可用模型，但不能保证长期兼容。
- [ ] **扫码登录依赖上游三个私有接口**：`sso.xfyun.cn` 的 `scanlogin/qrcode` 与 `scanlogin/uids`，以及 `bot/models/configs` 里的 `api_key`。上游若加验证码、签名或设备指纹，扫码登录会直接失效（届时只显示「登录暂不可用」），但已保存的凭据仍然可用。
- [ ] **扫码登录的凭据不会被主动刷新**：`ssoSessionId` 过期后需要重新扫码；插件不会拿它去换新（上游也没有公开的续期接口，客户端是重新登录）。
- [ ] **一个 DSH 只保存一个扫码登录**：后期换账号需要先「退出登录」再扫，不做多账号并存。
- [ ] **领取按钮依赖三个硬编码的客户端身份头**：`clientType`（平台）、`studioVersion` 与 `clientVersion`（后两者都是常量 `3.6.0`，跟随当前客户端版本）。上游一旦要求构建号、签名或设备指纹，这条路会立即失效，届时按钮只会显示「暂不可用」。
- [ ] **领取会替你对账号做一次客户端初始化**：`tenant-app/v2/init-app` 是桌面端启动时必调的接口，服务端在这一步结算当天的登录奖励。插件按同样的方式调用它——这既是领取能脱离客户端的原因，也意味着领取比“只读余额”更进一步，会主动触发一次服务端结算。上游若改变结算时机或要求额外的初始化参数，领取会失效，届时按钮报「暂不可用」而不会假装成功。
- [ ] **领取金额只能推算，不能读取**：当前客户端的弹窗 `payload` 不含金额，插件用 `init-app` 前后的余额差作为本次入账额。如果期间恰好在别处消耗了积分，差值会被低估，界面上的 `+N` 就只是下界；两次余额都读不到时不显示 `+N`。
- [ ] **CLI 的 `status` 会发起一次实时刷新**：它现在等待一次真实请求，才能如实报出目录来源与模型数；离线或未登录时报告 `empty` 与对应的失败原因。
- [ ] **不做账号切换跟随**：与 WorkBuddy 双 variant 不同，AStudio 只有一个产品，插件不复制 variant 级能力。

## 安全说明

- 从 AStudio 文件读到的凭证仅在内存中缓存，不写入任何文件；积分读取每次重新读会话文件（以便 AStudio 重新登录后立即生效），但只取 `ssoSessionId`。
- **唯一写入磁盘的凭据是插件自己扫码登录得到的会话**：`$DSH_HOME/.astudio-login.json`，权限 `0600`，只在用户按下「微信扫码登录」并完成扫码时写入，按下「退出登录」即删除。文件里的 `ssoSessionId` 与模型密钥不会出现在任何响应、界面或日志里；界面只显示账号 id 与昵称。
- shim 只绑定 `127.0.0.1`，不接受外部网络访问。
- 入站请求需通过 Host、Origin、Content-Type、Bearer 共享密钥四重校验；Host 校验挡住 DNS 重绑定。
- 共享密钥是每进程随机生成的 32 字节值，用 `timingSafeEqual` 做常量时间比较；真正的 AStudio token 只由凭证层解析，从不经过请求头。
- token 不会在任何界面或日志中回显；CLI 的异常信息会剥离形如 JWT 的串。
- 积分路由与状态路由同样做 loopback Host / Origin 双重校验，回包只含数字和状态，账户凭据始终留在宿主进程内。
- 账户侧写操作只有两条：领取路由只上报「今天的登录积分弹窗已完成」，不碰其它类型弹窗；登录路由只在扫码成功后写入上面那个文件。两条的回包里都只有状态与账号信息，没有凭据。
- 所有上游响应都视为不可信输入：流式读取带大小上限，路由回包在浏览器端重新校验后再渲染。

## 开发

```bash
npm install
npm run check      # typecheck + test + build
npm test           # 运行 302 个测试（29 个测试文件）
npm run build      # 产出 lib/（DSH 实际加载的目录）
```

`lib/` 里 `index.js` 是宿主入口，`client.js` 是浏览器 half，`bin.js` 是命令行。宿主与运行时依赖（pi-ai、cordis、schemastery、各 `dsh-*`）全部声明为 external，不打进 bundle，避免与 profile 里的宿主模块重复；浏览器侧只保留 React 为运行时依赖。

严格 TS，开启 `noUncheckedIndexedAccess` 与 `exactOptionalPropertyTypes`。
